## テーマ1: いいね機能とチャット連携（MVPの中核機能）

**該当項目**: #8（続報）, #17, #19, #21, #22, #23, #24

### 概要
「同人誌作家向けマッチングサービス」の中心となる機能。相手に「いいね」を送ると、その相手とだけチャットができるようになる、という一連の流れ。講義教材「第11回 作家マッチングアプリ実装ガイド」の設計（片思い型）に沿って実装した。

### Step1: いいね機能そのもの（もともと教材とほぼ同一の実装だった）
- `likes`テーブル（`from_user_id`・`to_user_id`・`created_at`）に「誰が誰にいいねしたか」を1行ずつ記録する、シンプルな構造
- `POST /likes`：いいねを送る。送信者IDはJWTから自動取得し、フロントからは`to_user_id`だけを送る
- `GET /likes/sent/{user_id}`：自分が送ったいいね一覧を取得
- この部分は大きな修正が発生しておらず、最初から教材通りの実装だった

### Step2（#8続報）: メッセージ機能を教材の「片思い型」設計に合わせる
**背景**: 一時期、`Matching`（マッチング成立）→`Chatroom`（1:1のチャットルーム）→`Message`という3段階の独自設計を作っていたが（詳細はテーマ5参照）、講義教材を確認したところ、教材は`Matching`という概念を使わず「`likes`に記録があれば即メッセージ送信可能」という、もっとシンプルな「片思い型」を採用していることが判明。今後の授業がこの設計を前提に進むため、Message機能のみ教材に合わせて方向転換した。

**変更内容**（`backend/app/models/message.py`）
```python
# 変更前（Chatroom経由の設計）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    chatroom_id = Column(Integer, ForeignKey("chatrooms.id"), nullable=False)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())

# 変更後（教材通り、sender_id/receiver_idの直接指定）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    receiver_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

`routers/message.py`では、`Depends(get_current_user)`を使い、送信者IDをフロントから送らせずJWTから自動取得する形にした（なりすまし防止）。

```python
@router.post("/", response_model=MessageResponse, status_code=201)
def create_message(
    message: MessageCreate,
    db: Session = Depends(get_db),
    current_user = Depends(get_current_user),
):
    return crud.create_message(db, message=message, sender_id=current_user.id)
```

会話の取得は、`sender_id`/`receiver_id`の両方向をORで検索する`get_conversation`関数を使用（`GET /messages/{user_id}/{other_user_id}`）。

**Alembicマイグレーション**: `messages`テーブルから`chatroom_id`を削除し`receiver_id`を追加。`chatrooms`/`matchings`テーブルへの変更は含まれないことを確認済み。既存データは0件だったため、そのまま適用成功。

**動作確認**（`curl`にて実施）: `POST /messages/`でリクエストボディに`sender_id`を含めなくても、レスポンスの`sender_id`が正しくログイン中ユーザーのIDになっていることを確認。`GET /messages/{user_id}/{other_user_id}`で送信したメッセージが時系列で取得できることも確認。途中、`routers/__init__.py`の中身が誤って`crud/__init__.py`の内容で上書きされコンテナが起動しないトラブルが発生したが、正しい内容に書き戻して解決。

## テーマ3: 認証・アクセス制御（ログイン・ミドルウェア）

**該当項目**: #3・#4

### 概要
ログインしていないユーザーが、見せたくないページに直接アクセスできてしまう問題への対応。

### 経緯（3段階で変化した）
1. **最初の状態**: `PROTECTED_PATHS`（保護対象パス）のリストに`/`（トップページ）が含まれておらず、未ログインでもトップページに入れてしまっていた
2. **修正の途中で新バグ**: 変数名を`PUBLIC_PATHS`に変えたが中身（保護パスのリスト）を変え忘れ、`/login`ページ自体がログイン必須ページとして扱われてしまい、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生
3. **最終形**: `PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外の全ページを保護する設計に統一

```typescript
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;
  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

### 補足（訂正した誤り）
`proxy.ts`というファイル名について、当初「`middleware.ts`にリネームすべき」と誤って助言したが、実際にはNext.js 16で`middleware.ts`から`proxy.ts`への名称変更が公式に行われており、リネーム不要だった。

### 現在の状態
✅ **完成**。未ログイン時は`/login`・`/register`以外の全ページで自動的にログイン画面へ誘導される。

## テーマ4: ユーザーの無効化（削除ボタンの500エラー対応）

**該当項目**: #5（#6は未着手）

### 概要
ユーザー一覧の「削除」ボタンを押すとエラーになる問題への対応。

### 原因
削除しようとしたユーザーが`likes`・`messages`テーブルで他のユーザーと紐付いていたため、データベースの整合性ルール（外部キー制約）に違反し、`IntegrityError`が発生していた。FastAPIは未処理の例外が起きるとCORSヘッダーを正しく付けられず、ブラウザ側では「CORSブロック」に見えていたが、実体はバックエンドの500エラーだった。

### 対応
物理削除（`DELETE`でレコードごと消す）をやめ、`is_active`フラグを`True`/`False`で切り替えるだけの**論理削除方式**に変更。バックエンド（`crud/user.py`, `routers/user.py`）に`deactivate_user`・`activate_user`という関数とPATCHエンドポイントを追加し、フロントエンド（`UserCard.tsx`等）の「削除」ボタンも「無効化」ボタンに置き換えた。

```python
def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user
```

一覧取得（`get_users`）だけ`is_active == True`でフィルタし、詳細取得・ログイン用の検索（`get_user`, `get_user_by_email`）はフィルタしない設計にした。これは、無効化された本人がログイン・自分のページへアクセスできなくなると、自力で再有効化する手段が失われてしまうための配慮。

### 現在の状態
✅ **完成・動作確認済み**。無効化したユーザーは一覧から消えるが、データは物理的に残るためFK制約違反も起きない。

**🟡 未着手（#6）**: `likes`/`messages`のFKに`ON DELETE CASCADE`が未設定。論理削除で回避済みだが、恒久対応としては残っている。

```python
# crud/matching.py（マッチング成立と同時にChatroomを自動作成）
def create_matching(db: Session, matching: MatchingCreate):
    db_matching = Matching(**matching.model_dump())
    db.add(db_matching)
    db.commit()
    db.refresh(db_matching)

    db_chatroom = Chatroom(matching_id=db_matching.id)
    db.add(db_chatroom)
    db.commit()

    return db_matching
```
