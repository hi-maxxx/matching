## テーマ1: いいね機能とチャット連携（MVPの中核機能）

### 概要
「同人誌作家向けマッチングサービス」の中心となる機能。相手に「いいね」を送ると、その相手とだけチャットができるようになる、という一連の流れ。講義教材「第11回 作家マッチングアプリ実装ガイド」の設計（片思い型）に沿って実装した。

### Step1: いいね機能そのもの（もともと教材とほぼ同一の実装だった）
- `likes`テーブル（`from_user_id`・`to_user_id`・`created_at`）に「誰が誰にいいねしたか」を1行ずつ記録する、シンプルな構造
- `POST /likes`：いいねを送る。送信者IDはJWTから自動取得し、フロントからは`to_user_id`だけを送る
- `GET /likes/sent/{user_id}`：自分が送ったいいね一覧を取得
- この部分は大きな修正が発生しておらず、最初から教材通りの実装だった

### Step2: メッセージ機能を教材の「片思い型」設計に合わせる
**背景**: 一時期、`Matching`（マッチング成立）→`Chatroom`（1:1のチャットルーム）→`Message`という3段階の独自設計を作っていたが、講義教材を確認したところ、教材は`Matching`という概念を使わず「`likes`に記録があれば即メッセージ送信可能」という、もっとシンプルな「片思い型」を採用していることが判明。今後の授業がこの設計を前提に進むため、Message機能のみ教材に合わせて方向転換した。

**変更内容**（`backend/app/models/message.py`）
```python
# 変更前（Chatroom経由の設計）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    chatroom_id = Column(Integer, ForeignKey("chatrooms.id"), nullable=False)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())

# 変更後（教材通り、sender_id/receiver_idの直接指定）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    receiver_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

`routers/message.py`では、`Depends(get_current_user)`を使い、送信者IDをフロントから送らせずJWTから自動取得する形にした（なりすまし防止）。

```python
@router.post("/", response_model=MessageResponse, status_code=201)
def create_message(
    message: MessageCreate,
    db: Session = Depends(get_db),
    current_user = Depends(get_current_user),
):
    return crud.create_message(db, message=message, sender_id=current_user.id)
```

会話の取得は、`sender_id`/`receiver_id`の両方向をORで検索する`get_conversation`関数を使用（`GET /messages/{user_id}/{other_user_id}`）。

### Step3: フロントエンドのチャット画面を新規実装
以下の4ファイルを新規作成・修正し、教材スライド11枚目の「吹き出し + 入力欄 + 送信ボタン」のUIを実現した。

| ファイル | 役割 |
|---|---|
| `types/message.ts` | `MessageCreate`/`MessageResponse`の型定義 |
| `hooks/useConversation.ts` | 会話の取得・送信ロジック。送信成功後は会話全体を取り直す（「画面をDBの鏡として扱う」教材の設計方針） |
| `app/messages/[userId]/page.tsx` | チャット画面本体。動的ルート（`[userId]`）で相手を指定 |
| `components/MatchCard.tsx` | マッチング相手一覧のカードに「チャット」ボタンを追加 |

自分のメッセージと相手のメッセージを区別する部分：
```tsx
const isMine = msg.sender_id === currentUserId;
// ...
<div className={`... ${isMine ? "bg-pink-600 text-white ml-auto" : "bg-gray-100 text-gray-900 mr-auto"}`}>
  {msg.content}
</div>
```
（`ml-auto`＝自分のメッセージを右に寄せる、`mr-auto`＝相手のメッセージを左に寄せる）

### Step4: 「いいね済みの相手とだけチャットできる」制限を追加
**背景**: Step3の実装直後は、いいねの有無に関わらず全員に「チャット」ボタンが表示されてしまっていた。教材の設計は「いいね送信によって連絡導線が開く」ことが前提だったため、UI上でもこれに合わせる必要があった。

**変更内容**（`MatchCard.tsx`）
```tsx
{liked ? (
  <Link href={`/messages/${user.id}`} className="... text-blue-600 border-blue-200 ...">
    チャット
  </Link>
) : (
  <button disabled title="いいねを送るとチャットできるようになります" className="... text-gray-300 ...">
    チャット
  </button>
)}
```
`liked`（いいね済みかどうか）が`true`の時だけ実際にチャット画面へ遷移できるリンクを表示し、`false`の時はクリックできないグレーアウトボタンにした。

### 付随する改善
- チャット画面に相手の名前を表示（`useUser(otherUserId)`フックを使用、それまでは誰とやり取りしているか画面上で分からなかった）
- トップページから`/matching`への導線ボタンを追加（`page.tsx`）
- **ログイン成功後の遷移先を`/`（トップページ）から`/matching`に変更**（`LoginForm.tsx`）。ログイン直後にMVPの中心導線へすぐアクセスできるようにした

### 現在の状態
✅ **完成・動作確認済み**（2026-08-02）。「マッチング相手一覧→いいね送信→チャットボタンが有効化→1対1でメッセージ送受信」という一連の流れが動くことをブラウザで確認済み。教材が定義するMVPの完成状態に到達している。

## テーマ2: プロフィール機能

### 概要
ユーザーが自分の情報（名前・自己紹介・性格など）を登録・編集できる機能。

### 新規登録時のハードコード削除
新規登録すると`penname`・`introduction`・`personality`・`work`・`phone`が本人の入力に関係なく全員「テスト」という固定文字列で登録されていた（開発初期の仮実装が残っていたと思われる）。`crud/user.py`の`create_user`からこれらの固定値を削除し、未入力（`NULL`）のまま登録されるよう修正。副次的に、DB側の`penname`カラムに残っていた`NOT NULL`制約もAlembicマイグレーションで解消した。

### プロフィールのインライン編集機能（personality追加）
`personality`（性格）がAPIのスキーマ（`UserUpdate`/`UserResponse`）に定義されておらず、更新も表示もできなかった。スキーマに追加し、トップページの`Topframe.tsx`で自己紹介文・性格をその場で編集できるUIを新規実装した（「編集する」ボタン→テキストエリア表示→「保存する」で`PUT /users/{id}`を実行）。

### アイコン・名前の実データ連動
トップページのプロフィールカードが、誰がログインしていても固定のプレースホルダー（「アイコン画像」「名前（ペンネーム）」という文字列）のままだった。`useAuth()`からログイン中ユーザーの`avatar_url`・`name`を取得し、実データを表示するよう修正した。

### 現在の状態
✅ **完成**（`personality`・`bio`・`avatar_url`・`name`は編集・表示可能）。`penname`・`introduction`・`work`・`phone`はまだUI側の編集機能が未実装（🟡課題として残存）。

## テーマ3: 認証・アクセス制御（ログイン・ミドルウェア）

### 概要
ログインしていないユーザーが、見せたくないページに直接アクセスできてしまう問題への対応。

### 経緯（3段階で変化した）
1. **最初の状態**: `PROTECTED_PATHS`（保護対象パス）のリストに`/`（トップページ）が含まれておらず、未ログインでもトップページに入れてしまっていた
2. **修正の途中で新バグ**: 変数名を`PUBLIC_PATHS`に変えたが中身（保護パスのリスト）を変え忘れ、`/login`ページ自体がログイン必須ページとして扱われてしまい、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生
3. **最終形**: `PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外の全ページを保護する設計に統一

```typescript
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;
  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }
  return NextResponse.next();
}
```

### 補足（訂正した誤り）
`proxy.ts`というファイル名について、当初「`middleware.ts`にリネームすべき」と誤って助言したが、実際にはNext.js 16で`middleware.ts`から`proxy.ts`への名称変更が公式に行われており、リネーム不要だった。

### 現在の状態
✅ **完成**。未ログイン時は`/login`・`/register`以外の全ページで自動的にログイン画面へ誘導される。

## テーマ4: ユーザーの無効化（削除ボタンの500エラー対応）

### 概要
ユーザー一覧の「削除」ボタンを押すとエラーになる問題への対応。

### 原因
削除しようとしたユーザーが`likes`・`messages`テーブルで他のユーザーと紐付いていたため、データベースの整合性ルール（外部キー制約）に違反し、`IntegrityError`が発生していた。FastAPIは未処理の例外が起きるとCORSヘッダーを正しく付けられず、ブラウザ側では「CORSブロック」に見えていたが、実体はバックエンドの500エラーだった。

### 対応
物理削除（`DELETE`でレコードごと消す）をやめ、`is_active`フラグを`True`/`False`で切り替えるだけの**論理削除方式**に変更。バックエンド（`crud/user.py`, `routers/user.py`）に`deactivate_user`・`activate_user`という関数とPATCHエンドポイントを追加し、フロントエンド（`UserCard.tsx`等）の「削除」ボタンも「無効化」ボタンに置き換えた。

一覧取得（`get_users`）だけ`is_active == True`でフィルタし、詳細取得・ログイン用の検索（`get_user`, `get_user_by_email`）はフィルタしない設計にした。これは、無効化された本人がログイン・自分のページへアクセスできなくなると、自力で再有効化する手段が失われてしまうための配慮。

### 現在の状態
✅ **完成・動作確認済み**。無効化したユーザーは一覧から消えるが、データは物理的に残るためFK制約違反も起きない。

## テーマ5: Chatroom/Matching設計（現在は保留中）

### 概要
「マッチング成立→専用チャットルーム作成→メッセージ」という、教材とは異なる独自設計を一度作ったが、教材の設計（テーマ1参照）と食い違うことが判明し、Message機能のみ方向転換した経緯。

### 経緯
1. `Chatroom`モデルが当初、謎の`chatroom_id`カラムを持つなど設計が不明瞭だった
2. `Matching`→`Chatroom`（1:1、自動作成）→`Message`という構造に再設計し、Alembicマイグレーションも実施
3. その後、講義教材が`likes`ベースの「片思い型」を前提にしていることが判明し、**Message機能だけ**教材の設計（`sender_id`/`receiver_id`直接指定）に戻した
4. `Chatroom`・`Matching`関連のモデル・CRUD・ルーターは、コード自体は変更せず**「休眠中」として残置**している

### 現在の状態
🟡 **保留中**。`models/chatroom.py`, `models/matching.py`と付随するコードは実際には使われていないが、削除もしていない。将来的に「相互承認型（双方がいいねしたら初めてマッチ成立）」のような拡張をする際の土台として残すか、使わないなら整理して削除するか、方針を決める必要がある。
