## テーマ1: いいね機能とチャット連携（MVPの中核機能）

**該当項目**: #8（続報）, #17, #19, #21, #22, #23, #24

### 概要
「同人誌作家向けマッチングサービス」の中心となる機能。相手に「いいね」を送ると、その相手とだけチャットができるようになる、という一連の流れ。講義教材「第11回 作家マッチングアプリ実装ガイド」の設計（片思い型）に沿って実装した。

### Step1: いいね機能そのもの（もともと教材とほぼ同一の実装だった）
- `likes`テーブル（`from_user_id`・`to_user_id`・`created_at`）に「誰が誰にいいねしたか」を1行ずつ記録する、シンプルな構造
- `POST /likes`：いいねを送る。送信者IDはJWTから自動取得し、フロントからは`to_user_id`だけを送る
- `GET /likes/sent/{user_id}`：自分が送ったいいね一覧を取得
- この部分は大きな修正が発生しておらず、最初から教材通りの実装だった

### Step2（#8続報）: メッセージ機能を教材の「片思い型」設計に合わせる
**背景**: 一時期、`Matching`（マッチング成立）→`Chatroom`（1:1のチャットルーム）→`Message`という3段階の独自設計を作っていたが（詳細はテーマ5参照）、講義教材を確認したところ、教材は`Matching`という概念を使わず「`likes`に記録があれば即メッセージ送信可能」という、もっとシンプルな「片思い型」を採用していることが判明。今後の授業がこの設計を前提に進むため、Message機能のみ教材に合わせて方向転換した。

**変更内容**（`backend/app/models/message.py`）
```python
# 変更前（Chatroom経由の設計）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    chatroom_id = Column(Integer, ForeignKey("chatrooms.id"), nullable=False)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())

# 変更後（教材通り、sender_id/receiver_idの直接指定）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    receiver_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

`routers/message.py`では、`Depends(get_current_user)`を使い、送信者IDをフロントから送らせずJWTから自動取得する形にした（なりすまし防止）。

```python

def create_message(
    message: MessageCreate,
    db: Session = Depends(get_db),
    current_user = Depends(get_current_user),
):
    return crud.create_message(db, message=message, sender_id=current_user.id)
```

会話の取得は、`sender_id`/`receiver_id`の両方向をORで検索する`get_conversation`関数を使用（`GET /messages/{user_id}/{other_user_id}`）。

**Alembicマイグレーション**: `messages`テーブルから`chatroom_id`を削除し`receiver_id`を追加。`chatrooms`/`matchings`テーブルへの変更は含まれないことを確認済み。既存データは0件だったため、そのまま適用成功。

**動作確認**（`curl`にて実施）: `POST /messages/`でリクエストボディに`sender_id`を含めなくても、レスポンスの`sender_id`が正しくログイン中ユーザーのIDになっていることを確認。`GET /messages/{user_id}/{other_user_id}`で送信したメッセージが時系列で取得できることも確認。途中、`routers/__init__.py`の中身が誤って`crud/__init__.py`の内容で上書きされコンテナが起動しないトラブルが発生したが、正しい内容に書き戻して解決。

## テーマ3: 認証・アクセス制御（ログイン・ミドルウェア）

**該当項目**: #3・#4

### 概要
ログインしていないユーザーが、見せたくないページに直接アクセスできてしまう問題への対応。

### 経緯（3段階で変化した）
1. **最初の状態**: `PROTECTED_PATHS`（保護対象パス）のリストに`/`（トップページ）が含まれておらず、未ログインでもトップページに入れてしまっていた
2. **修正の途中で新バグ**: 変数名を`PUBLIC_PATHS`に変えたが中身（保護パスのリスト）を変え忘れ、`/login`ページ自体がログイン必須ページとして扱われてしまい、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生
3. **最終形**: `PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外の全ページを保護する設計に統一

```typescript
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;
  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

### 補足（訂正した誤り）
`proxy.ts`というファイル名について、当初「`middleware.ts`にリネームすべき」と誤って助言したが、実際にはNext.js 16で`middleware.ts`から`proxy.ts`への名称変更が公式に行われており、リネーム不要だった。

### 現在の状態
✅ **完成**。未ログイン時は`/login`・`/register`以外の全ページで自動的にログイン画面へ誘導される。

## テーマ4: ユーザーの無効化（削除ボタンの500エラー対応）

**該当項目**: #5（#6は未着手）

### 概要
ユーザー一覧の「削除」ボタンを押すとエラーになる問題への対応。

### 原因
削除しようとしたユーザーが`likes`・`messages`テーブルで他のユーザーと紐付いていたため、データベースの整合性ルール（外部キー制約）に違反し、`IntegrityError`が発生していた。FastAPIは未処理の例外が起きるとCORSヘッダーを正しく付けられず、ブラウザ側では「CORSブロック」に見えていたが、実体はバックエンドの500エラーだった。

### 対応
物理削除（`DELETE`でレコードごと消す）をやめ、`is_active`フラグを`True`/`False`で切り替えるだけの**論理削除方式**に変更。バックエンド（`crud/user.py`, `routers/user.py`）に`deactivate_user`・`activate_user`という関数とPATCHエンドポイントを追加し、フロントエンド（`UserCard.tsx`等）の「削除」ボタンも「無効化」ボタンに置き換えた。

```python
def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user
```

一覧取得（`get_users`）だけ`is_active == True`でフィルタし、詳細取得・ログイン用の検索（`get_user`, `get_user_by_email`）はフィルタしない設計にした。これは、無効化された本人がログイン・自分のページへアクセスできなくなると、自力で再有効化する手段が失われてしまうための配慮。

### 現在の状態
✅ **完成・動作確認済み**。無効化したユーザーは一覧から消えるが、データは物理的に残るためFK制約違反も起きない。

**🟡 未着手（#6）**: `likes`/`messages`のFKに`ON DELETE CASCADE`が未設定。論理削除で回避済みだが、恒久対応としては残っている。

```python
# crud/matching.py（マッチング成立と同時にChatroomを自動作成）
def create_matching(db: Session, matching: MatchingCreate):

    db.add(db_matching)
    db.commit()
    db.refresh(db_matching)

    db_chatroom = Chatroom(matching_id=db_matching.id)
    db.add(db_chatroom)
    db.commit()

    return db_matching
```

## テーマ1: いいね機能とチャット連携（MVPの中核機能）

### 概要
「同人誌作家向けマッチングサービス」の中心となる機能。相手に「いいね」を送ると、その相手とだけチャットができるようになる、という一連の流れ。講義教材「第11回 作家マッチングアプリ実装ガイド」の設計（片思い型）に沿って実装した。

### Step1: いいね機能そのもの（もともと教材とほぼ同一の実装だった）
- `likes`テーブル（`from_user_id`・`to_user_id`・`created_at`）に「誰が誰にいいねしたか」を1行ずつ記録する、シンプルな構造
- `POST /likes`：いいねを送る。送信者IDはJWTから自動取得し、フロントからは`to_user_id`だけを送る
- `GET /likes/sent/{user_id}`：自分が送ったいいね一覧を取得
- この部分は大きな修正が発生しておらず、最初から教材通りの実装だった

### Step2: メッセージ機能を教材の「片思い型」設計に合わせる
**背景**: 一時期、`Matching`（マッチング成立）→`Chatroom`（1:1のチャットルーム）→`Message`という3段階の独自設計を作っていたが、講義教材を確認したところ、教材は`Matching`という概念を使わず「`likes`に記録があれば即メッセージ送信可能」という、もっとシンプルな「片思い型」を採用していることが判明。今後の授業がこの設計を前提に進むため、Message機能のみ教材に合わせて方向転換した。

**変更内容**（`backend/app/models/message.py`）
```python
# 変更前（Chatroom経由の設計）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    chatroom_id = Column(Integer, ForeignKey("chatrooms.id"), nullable=False)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())

# 変更後（教材通り、sender_id/receiver_idの直接指定）
class Message(Base):
    __tablename__ = "messages"
    id = Column(Integer, primary_key=True, index=True)
    sender_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    receiver_id = Column(Integer, ForeignKey("users.id"), nullable=False)
    content = Column(Text, nullable=False)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

`routers/message.py`では、`Depends(get_current_user)`を使い、送信者IDをフロントから送らせずJWTから自動取得する形にした（なりすまし防止）。

## テーマ3: 認証・アクセス制御（ログイン・ミドルウェア）

### 概要
ログインしていないユーザーが、見せたくないページに直接アクセスできてしまう問題への対応。

### 経緯（3段階で変化した）
1. **最初の状態**: `PROTECTED_PATHS`（保護対象パス）のリストに`/`（トップページ）が含まれておらず、未ログインでもトップページに入れてしまっていた
2. **修正の途中で新バグ**: 変数名を`PUBLIC_PATHS`に変えたが中身（保護パスのリスト）を変え忘れ、`/login`ページ自体がログイン必須ページとして扱われてしまい、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生
3. **最終形**: `PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外の全ページを保護する設計に統一

```typescript
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;
  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }
  return NextResponse.next();
}
```

### 補足（訂正した誤り）
`proxy.ts`というファイル名について、当初「`middleware.ts`にリネームすべき」と誤って助言したが、実際にはNext.js 16で`middleware.ts`から`proxy.ts`への名称変更が公式に行われており、リネーム不要だった。

### 現在の状態
✅ **完成**。未ログイン時は`/login`・`/register`以外の全ページで自動的にログイン画面へ誘導される。

## テーマ4: ユーザーの無効化（削除ボタンの500エラー対応）

### 概要
ユーザー一覧の「削除」ボタンを押すとエラーになる問題への対応。

### 原因
削除しようとしたユーザーが`likes`・`messages`テーブルで他のユーザーと紐付いていたため、データベースの整合性ルール（外部キー制約）に違反し、`IntegrityError`が発生していた。FastAPIは未処理の例外が起きるとCORSヘッダーを正しく付けられず、ブラウザ側では「CORSブロック」に見えていたが、実体はバックエンドの500エラーだった。

### 対応
物理削除（`DELETE`でレコードごと消す）をやめ、`is_active`フラグを`True`/`False`で切り替えるだけの**論理削除方式**に変更。バックエンド（`crud/user.py`, `routers/user.py`）に`deactivate_user`・`activate_user`という関数とPATCHエンドポイントを追加し、フロントエンド（`UserCard.tsx`等）の「削除」ボタンも「無効化」ボタンに置き換えた。

一覧取得（`get_users`）だけ`is_active == True`でフィルタし、詳細取得・ログイン用の検索（`get_user`, `get_user_by_email`）はフィルタしない設計にした。これは、無効化された本人がログイン・自分のページへアクセスできなくなると、自力で再有効化する手段が失われてしまうための配慮。

### 現在の状態
✅ **完成・動作確認済み**。無効化したユーザーは一覧から消えるが、データは物理的に残るためFK制約違反も起きない。

### ✅ #1 実施内容: `create_user`のハードコード削除

```python
def create_user(db: Session, user: UserCreate):
    """ユーザー作成"""
    db_user = User(
        name=user.name,
        email=user.email,
        hashed_password=hash_password(user.password),
```

### ✅ #3・#4 訂正の経緯と最終コード

**当初の誤った助言**: 「`proxy.ts`という名前ではNext.jsに認識されないので`middleware.ts`にリネームすべき」と助言したが、これは誤りだった。

**訂正**: Next.js 16で、Express.jsのミドルウェアとの混同を避ける目的で、公式に`middleware.ts` → `proxy.ts`への名称変更が行われている（`next@16.2.7`はこの仕様に対応済みバージョン）。したがって`proxy.ts`のままで正しく、リネームは不要だった。

**実装上の実際のバグ**: ファイル名ではなく、ロジック側に問題があった。

- 当初のコード: `PROTECTED_PATHS = ["/profile", "/matching", "/chat"]`という「保護パス方式」で、`/`や`/login`が対象外だったため、未ログインでもトップページに入れてしまっていた。
- 1回目の修正で`PUBLIC_PATHS`という名前に変えたが中身は保護パスのままで、`/login`自体がログイン必須ページ扱いになり、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生した。
- 最終的に、`PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外は全てログイン必須という設計に変更して解決。

**最終コード**（`src/proxy.ts`）:
```typescript
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

// ログイン不要でアクセスできるパス
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;

  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**動作確認済み**: 未ログインで`/`や`/login`以外にアクセス→`/login`へリダイレクト。ログイン済みで`/login`・`/register`にアクセス→`/`へリダイレクト。無限ループは解消。

### ✅ #5 実施内容: 物理削除 → 論理削除（is_active切り替え）方式への変更

**背景**: 削除ボタン押下時に`Failed to fetch`エラーが発生。実体はバックエンドの500エラー（FastAPI/StarletteはCORSMiddleware内側で未処理例外が起きるとCORSヘッダーを付与できず、ブラウザ側では「CORSブロック」に見えていた）。真因は、削除対象ユーザーが`likes`/`messages`テーブルで他ユーザーと紐付いており、`ON DELETE CASCADE`未設定のため`db.delete(db_user)`時に外部キー制約違反（IntegrityError）が発生していたこと。

**対応方針**: 物理削除ではなく`is_active`フラグを`False`にする論理削除方式に変更（FK制約の問題を根本的に回避）。

**Backend**

`crud/user.py`: 一覧・詳細取得のフィルタ方針を整理し、無効化・有効化の関数を追加。
```python
def get_users(db: Session, skip: int = 0, limit: int = 100):
    """ユーザー一覧取得（有効なユーザーのみ）"""
    return db.query(User).filter(User.is_active == True).offset(skip).limit(limit).all()

def get_user(db: Session, user_id: int):
    """ユーザー1件取得（無効化されていてもアクセス可・本人の再有効化用）"""
    return db.query(User).filter(User.id == user_id).first()

def get_user_by_email(db: Session, email: str):
    """メールアドレスでユーザーを検索（無効化されていてもログイン可能にする）"""
    return db.query(User).filter(User.email == email).first()

def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user

def activate_user(db: Session, user_id: int):
    """ユーザーを有効化"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = True
        db.commit()
        db.refresh(db_user)
    return db_user
```

> 設計判断: `get_users`（一覧）のみ`is_active`でフィルタし、`get_user`（詳細）・`get_user_by_email`（ログイン認証）はフィルタしない方針にした。理由は、無効化されたユーザーもログイン・自分のプロフィールへのアクセスはできるようにし、自分で再有効化できる導線を残すため。

### ✅ #3・#4 訂正の経緯と最終コード

**当初の誤った助言**: 「`proxy.ts`という名前ではNext.jsに認識されないので`middleware.ts`にリネームすべき」と助言したが、これは誤りだった。

**訂正**: Next.js 16で、Express.jsのミドルウェアとの混同を避ける目的で、公式に`middleware.ts` → `proxy.ts`への名称変更が行われている（`next@16.2.7`はこの仕様に対応済みバージョン）。したがって`proxy.ts`のままで正しく、リネームは不要だった。

**実装上の実際のバグ**: ファイル名ではなく、ロジック側に問題があった。

- 当初のコード: `PROTECTED_PATHS = ["/profile", "/matching", "/chat"]`という「保護パス方式」で、`/`や`/login`が対象外だったため、未ログインでもトップページに入れてしまっていた。
- 1回目の修正で`PUBLIC_PATHS`という名前に変えたが中身は保護パスのままで、`/login`自体がログイン必須ページ扱いになり、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生した。
- 最終的に、`PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外は全てログイン必須という設計に変更して解決。

**最終コード**（`src/proxy.ts`）:
```typescript
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

// ログイン不要でアクセスできるパス
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;

  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**動作確認済み**: 未ログインで`/`や`/login`以外にアクセス→`/login`へリダイレクト。ログイン済みで`/login`・`/register`にアクセス→`/`へリダイレクト。無限ループは解消。

### ✅ #5 実施内容: 物理削除 → 論理削除（is_active切り替え）方式への変更

**背景**: 削除ボタン押下時に`Failed to fetch`エラーが発生。実体はバックエンドの500エラー（FastAPI/StarletteはCORSMiddleware内側で未処理例外が起きるとCORSヘッダーを付与できず、ブラウザ側では「CORSブロック」に見えていた）。真因は、削除対象ユーザーが`likes`/`messages`テーブルで他ユーザーと紐付いており、`ON DELETE CASCADE`未設定のため`db.delete(db_user)`時に外部キー制約違反（IntegrityError）が発生していたこと。

**対応方針**: 物理削除ではなく`is_active`フラグを`False`にする論理削除方式に変更（FK制約の問題を根本的に回避）。

**Backend**

`crud/user.py`: 一覧・詳細取得のフィルタ方針を整理し、無効化・有効化の関数を追加。
```python
def get_users(db: Session, skip: int = 0, limit: int = 100):
    """ユーザー一覧取得（有効なユーザーのみ）"""
    return db.query(User).filter(User.is_active == True).offset(skip).limit(limit).all()

def get_user(db: Session, user_id: int):
    """ユーザー1件取得（無効化されていてもアクセス可・本人の再有効化用）"""
    return db.query(User).filter(User.id == user_id).first()

def get_user_by_email(db: Session, email: str):
    """メールアドレスでユーザーを検索（無効化されていてもログイン可能にする）"""
    return db.query(User).filter(User.email == email).first()

def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user

def activate_user(db: Session, user_id: int):
    """ユーザーを有効化"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = True
        db.commit()
        db.refresh(db_user)
    return db_user
```

### ✅ #3・#4 訂正の経緯と最終コード

**当初の誤った助言**: 「`proxy.ts`という名前ではNext.jsに認識されないので`middleware.ts`にリネームすべき」と助言したが、これは誤りだった。

**訂正**: Next.js 16で、Express.jsのミドルウェアとの混同を避ける目的で、公式に`middleware.ts` → `proxy.ts`への名称変更が行われている（`next@16.2.7`はこの仕様に対応済みバージョン）。したがって`proxy.ts`のままで正しく、リネームは不要だった。

**実装上の実際のバグ**: ファイル名ではなく、ロジック側に問題があった。

- 当初のコード: `PROTECTED_PATHS = ["/profile", "/matching", "/chat"]`という「保護パス方式」で、`/`や`/login`が対象外だったため、未ログインでもトップページに入れてしまっていた。
- 1回目の修正で`PUBLIC_PATHS`という名前に変えたが中身は保護パスのままで、`/login`自体がログイン必須ページ扱いになり、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生した。
- 最終的に、`PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外は全てログイン必須という設計に変更して解決。

**最終コード**（`src/proxy.ts`）:
```typescript
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

// ログイン不要でアクセスできるパス
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;

  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**動作確認済み**: 未ログインで`/`や`/login`以外にアクセス→`/login`へリダイレクト。ログイン済みで`/login`・`/register`にアクセス→`/`へリダイレクト。無限ループは解消。

### ✅ #5 実施内容: 物理削除 → 論理削除（is_active切り替え）方式への変更

**背景**: 削除ボタン押下時に`Failed to fetch`エラーが発生。実体はバックエンドの500エラー（FastAPI/StarletteはCORSMiddleware内側で未処理例外が起きるとCORSヘッダーを付与できず、ブラウザ側では「CORSブロック」に見えていた）。真因は、削除対象ユーザーが`likes`/`messages`テーブルで他ユーザーと紐付いており、`ON DELETE CASCADE`未設定のため`db.delete(db_user)`時に外部キー制約違反（IntegrityError）が発生していたこと。

**対応方針**: 物理削除ではなく`is_active`フラグを`False`にする論理削除方式に変更（FK制約の問題を根本的に回避）。

**Backend**

```python
def get_user(db: Session, user_id: int):
    """ユーザー1件取得（無効化されていてもアクセス可・本人の再有効化用）"""
    return db.query(User).filter(User.id == user_id).first()

def get_user_by_email(db: Session, email: str):
    """メールアドレスでユーザーを検索（無効化されていてもログイン可能にする）"""
    return db.query(User).filter(User.email == email).first()

def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user

def activate_user(db: Session, user_id: int):
    """ユーザーを有効化"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = True
        db.commit()
        db.refresh(db_user)
    return db_user
```

```
Message:  id, chatroom_id（FK）, sender_id（FK）, content, created_at
```

### ✅ #3・#4 訂正の経緯と最終コード

**当初の誤った助言**: 「`proxy.ts`という名前ではNext.jsに認識されないので`middleware.ts`にリネームすべき」と助言したが、これは誤りだった。

**訂正**: Next.js 16で、Express.jsのミドルウェアとの混同を避ける目的で、公式に`middleware.ts` → `proxy.ts`への名称変更が行われている（`next@16.2.7`はこの仕様に対応済みバージョン）。したがって`proxy.ts`のままで正しく、リネームは不要だった。

**実装上の実際のバグ**: ファイル名ではなく、ロジック側に問題があった。

- 当初のコード: `PROTECTED_PATHS = ["/profile", "/matching", "/chat"]`という「保護パス方式」で、`/`や`/login`が対象外だったため、未ログインでもトップページに入れてしまっていた。
- 1回目の修正で`PUBLIC_PATHS`という名前に変えたが中身は保護パスのままで、`/login`自体がログイン必須ページ扱いになり、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生した。
- 最終的に、`PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外は全てログイン必須という設計に変更して解決。

**最終コード**（`src/proxy.ts`）:
```typescript
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

// ログイン不要でアクセスできるパス
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;

  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**動作確認済み**: 未ログインで`/`や`/login`以外にアクセス→`/login`へリダイレクト。ログイン済みで`/login`・`/register`にアクセス→`/`へリダイレクト。無限ループは解消。

### ✅ #5 実施内容: 物理削除 → 論理削除（is_active切り替え）方式への変更

**背景**: 削除ボタン押下時に`Failed to fetch`エラーが発生。実体はバックエンドの500エラー（FastAPI/StarletteはCORSMiddleware内側で未処理例外が起きるとCORSヘッダーを付与できず、ブラウザ側では「CORSブロック」に見えていた）。真因は、削除対象ユーザーが`likes`/`messages`テーブルで他ユーザーと紐付いており、`ON DELETE CASCADE`未設定のため`db.delete(db_user)`時に外部キー制約違反（IntegrityError）が発生していたこと。

**対応方針**: 物理削除ではなく`is_active`フラグを`False`にする論理削除方式に変更（FK制約の問題を根本的に回避）。

**Backend**

`crud/user.py`: 一覧・詳細取得のフィルタ方針を整理し、無効化・有効化の関数を追加。
```python
def get_users(db: Session, skip: int = 0, limit: int = 100):
    """ユーザー一覧取得（有効なユーザーのみ）"""
    return db.query(User).filter(User.is_active == True).offset(skip).limit(limit).all()

def get_user(db: Session, user_id: int):
    """ユーザー1件取得（無効化されていてもアクセス可・本人の再有効化用）"""
    return db.query(User).filter(User.id == user_id).first()

def get_user_by_email(db: Session, email: str):
    """メールアドレスでユーザーを検索（無効化されていてもログイン可能にする）"""
    return db.query(User).filter(User.email == email).first()

def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user

def activate_user(db: Session, user_id: int):
    """ユーザーを有効化"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = True
        db.commit()
        db.refresh(db_user)
    return db_user
```

> 設計判断: `get_users`（一覧）のみ`is_active`でフィルタし、`get_user`（詳細）・`get_user_by_email`（ログイン認証）はフィルタしない方針にした。理由は、無効化されたユーザーもログイン・自分のプロフィールへのアクセスはできるようにし、自分で再有効化できる導線を残すため。

### ✅ #8 実施内容: Chatroom/Message設計をmatching_id/chatroom_idベースに再設計

### ✅ #1 実施内容: `create_user`のハードコード削除

**修正前**: `phone`/`penname`/`introduction`/`personality`/`work`が全て`"テスト"`固定で登録されていた。

**修正後**（`crud/user.py`）:
```python
def create_user(db: Session, user: UserCreate):
    """ユーザー作成"""
    db_user = User(
        name=user.name,
        email=user.email,
        hashed_password=hash_password(user.password),
    )
    db.add(db_user)
    db.commit()
    db.refresh(db_user)
    return db_user
```

`"テスト"`固定の項目を削除。`models/user.py`側ではこれらのカラムはもともと`nullable`扱いなので、モデル側の変更は不要で`crud/user.py`の`create_user`だけ直せばよかった。

**発生した副次トラブルと対応**:
DB上の`penname`カラムに実テーブルレベルで`NOT NULL`制約が残っており（モデル定義は`nullable=True`だったが未反映）、新規登録が`IntegrityError`で失敗した。Alembicマイグレーションで解消。

```bash
docker compose exec backend alembic revision --autogenerate -m "allow null in penname"
docker compose exec backend alembic upgrade head
```
→ `penname`が`NULL`許可になり、新規登録が正常に通ることを確認済み。

### ✅ #3・#4 訂正の経緯と最終コード

**当初の誤った助言**: 「`proxy.ts`という名前ではNext.jsに認識されないので`middleware.ts`にリネームすべき」と助言したが、これは誤りだった。

**訂正**: Next.js 16で、Express.jsのミドルウェアとの混同を避ける目的で、公式に`middleware.ts` → `proxy.ts`への名称変更が行われている（`next@16.2.7`はこの仕様に対応済みバージョン）。したがって`proxy.ts`のままで正しく、リネームは不要だった。

**実装上の実際のバグ**: ファイル名ではなく、ロジック側に問題があった。

- 当初のコード: `PROTECTED_PATHS = ["/profile", "/matching", "/chat"]`という「保護パス方式」で、`/`や`/login`が対象外だったため、未ログインでもトップページに入れてしまっていた。
- 1回目の修正で`PUBLIC_PATHS`という名前に変えたが中身は保護パスのままで、`/login`自体がログイン必須ページ扱いになり、無限リダイレクトループ（`ERR_TOO_MANY_REDIRECTS`）が発生した。
- 最終的に、`PUBLIC_PATHS`の中身を実際に「ログイン不要な公開ページ（`/login`・`/register`）」に修正し、それ以外は全てログイン必須という設計に変更して解決。

**最終コード**（`src/proxy.ts`）:
```typescript
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

// ログイン不要でアクセスできるパス
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;

  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**動作確認済み**: 未ログインで`/`や`/login`以外にアクセス→`/login`へリダイレクト。ログイン済みで`/login`・`/register`にアクセス→`/`へリダイレクト。無限ループは解消。

### ✅ #5 実施内容: 物理削除 → 論理削除（is_active切り替え）方式への変更

**背景**: 削除ボタン押下時に`Failed to fetch`エラーが発生。実体はバックエンドの500エラー（FastAPI/StarletteはCORSMiddleware内側で未処理例外が起きるとCORSヘッダーを付与できず、ブラウザ側では「CORSブロック」に見えていた）。真因は、削除対象ユーザーが`likes`/`messages`テーブルで他ユーザーと紐付いており、`ON DELETE CASCADE`未設定のため`db.delete(db_user)`時に外部キー制約違反（IntegrityError）が発生していたこと。

**対応方針**: 物理削除ではなく`is_active`フラグを`False`にする論理削除方式に変更（FK制約の問題を根本的に回避）。

**Backend**

`crud/user.py`: 一覧・詳細取得のフィルタ方針を整理し、無効化・有効化の関数を追加。
```python
def get_users(db: Session, skip: int = 0, limit: int = 100):
    """ユーザー一覧取得（有効なユーザーのみ）"""
    return db.query(User).filter(User.is_active == True).offset(skip).limit(limit).all()

def get_user(db: Session, user_id: int):
    """ユーザー1件取得（無効化されていてもアクセス可・本人の再有効化用）"""
    return db.query(User).filter(User.id == user_id).first()

def get_user_by_email(db: Session, email: str):
    """メールアドレスでユーザーを検索（無効化されていてもログイン可能にする）"""
    return db.query(User).filter(User.email == email).first()

def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user

def activate_user(db: Session, user_id: int):
    """ユーザーを有効化"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = True
        db.commit()
        db.refresh(db_user)
    return db_user
```

> 設計判断: `get_users`（一覧）のみ`is_active`でフィルタし、`get_user`（詳細）・`get_user_by_email`（ログイン認証）はフィルタしない方針にした。理由は、無効化されたユーザーもログイン・自分のプロフィールへのアクセスはできるようにし、自分で再有効化できる導線を残すため。

### ✅ #8 実施内容: Chatroom/Message設計をmatching_id/chatroom_idベースに再設計

**方針確認**（本人回答）:
- マッチング成立 = チャットルーム自動作成（1:1）でよい
- チャットは1つのマッチング相手との連続したスレッド（LINEのトーク画面イメージ）
- 常に1対1、グループチャットは想定しない → `Chatroom`に`user_id1`/`user_id2`を直接持たせるのではなく、シンプルに`matching_id`のみ持つ設計に

**新しいテーブル構造**:
```
Matching: id, user_id1, user_id2, created_at
Chatroom: id, matching_id（FK, UNIQUE）, created_at
Message:  id, chatroom_id（FK）, sender_id（FK）, content, created_at
```

**Backend変更内容**

`models/chatroom.py`: `user_id1`/`user_id2`/`chatroom_id`を削除し`matching_id`（`ForeignKey("matchings.id")`, `unique=True`）に変更。
`models/message.py`: `receiver_id`を削除し`chatroom_id`（`ForeignKey("chatrooms.id")`）を追加。

`schemas/chatroom.py`・`schemas/message.py`: モデルに合わせて`matching_id`/`chatroom_id`ベースに変更。

`crud/chatroom.py`: `create_chatroom`を`matching_id`のみで作成する形に単純化。`get_chatroom_by_matching_id`を新規追加。

`crud/matching.py`: `create_matching`内で、`Matching`保存直後に対応する`Chatroom`を自動作成する処理を追加。
```python
def create_matching(db: Session, matching: MatchingCreate):
    db_matching = Matching(**matching.model_dump())
    db.add(db_matching)
    db.commit()
    db.refresh(db_matching)

    db_chatroom = Chatroom(matching_id=db_matching.id)
    db.add(db_chatroom)
    db.commit()

    return db_matching
```

`crud/message.py`: `get_conversation`（`user_id`/`other_user_id`で検索）を削除し、`get_messages_by_chatroom`（`chatroom_id`のみで検索）に置き換え。`or_`/`and_`を使った複雑な条件分岐が不要になりシンプル化。

`crud/__init__.py`: 新規関数のインポートを反映。

`routers/chatroom.py`: `POST /chatrooms/`（手動作成用）を削除（自動作成されるため不要に）。代わりに`GET /chatrooms/by-matching/{matching_id}`を追加。

`routers/message.py`: `GET /messages/{user_id}/{other_user_id}` → `GET /messages/chatroom/{chatroom_id}`に変更。

**Alembicマイグレーションで発生したトラブルと対応**:
1. 過去に作成した「中身が空のマイグレーションファイル」を未適用のまま放置していたため、`--autogenerate`が`Target database is not up to date`エラーで失敗。`alembic upgrade head`で一度DBを最新の状態に追いつかせてから、改めて`--autogenerate`を実行して解決。
2. 生成されたマイグレーションが`chatrooms`/`messages`に`nullable=False`の新カラムを追加する内容だったため、既存のテストデータ（`chatrooms`3件、`messages`1件）が残ったままだと失敗する状態だった。事前に`TRUNCATE TABLE messages, chatrooms RESTART IDENTITY CASCADE;`でテーブルを空にしてから`alembic upgrade head`を実行し、成功。

**動作確認**: マイグレーション適用済み（`alembic current`が新しいリビジョンIDになっていることを確認）。API経由での動作確認（`POST /matchings/`→`Chatroom`自動作成→`GET /chatrooms/by-matching/{id}`→`POST /messages/`→`GET /messages/chatroom/{id}`）は次のステップで実施予定。

**最終コード**（`src/proxy.ts`）:
```typescript
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

// ログイン不要でアクセスできるパス
const PUBLIC_PATHS = ["/login", "/register"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;

  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**動作確認済み**: 未ログインで`/`や`/login`以外にアクセス→`/login`へリダイレクト。ログイン済みで`/login`・`/register`にアクセス→`/`へリダイレクト。無限ループは解消。

### ✅ #5 実施内容: 物理削除 → 論理削除（is_active切り替え）方式への変更

**背景**: 削除ボタン押下時に`Failed to fetch`エラーが発生。実体はバックエンドの500エラー（FastAPI/StarletteはCORSMiddleware内側で未処理例外が起きるとCORSヘッダーを付与できず、ブラウザ側では「CORSブロック」に見えていた）。真因は、削除対象ユーザーが`likes`/`messages`テーブルで他ユーザーと紐付いており、`ON DELETE CASCADE`未設定のため`db.delete(db_user)`時に外部キー制約違反（IntegrityError）が発生していたこと。

**対応方針**: 物理削除ではなく`is_active`フラグを`False`にする論理削除方式に変更（FK制約の問題を根本的に回避）。

**Backend**

`crud/user.py`: 一覧・詳細取得のフィルタ方針を整理し、無効化・有効化の関数を追加。
```python
def get_users(db: Session, skip: int = 0, limit: int = 100):
    """ユーザー一覧取得（有効なユーザーのみ）"""
    return db.query(User).filter(User.is_active == True).offset(skip).limit(limit).all()

def get_user(db: Session, user_id: int):
    """ユーザー1件取得（無効化されていてもアクセス可・本人の再有効化用）"""
    return db.query(User).filter(User.id == user_id).first()

def get_user_by_email(db: Session, email: str):
    """メールアドレスでユーザーを検索（無効化されていてもログイン可能にする）"""
    return db.query(User).filter(User.email == email).first()

def deactivate_user(db: Session, user_id: int):
    """ユーザーを無効化（論理削除）"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = False
        db.commit()
        db.refresh(db_user)
    return db_user

def activate_user(db: Session, user_id: int):
    """ユーザーを有効化"""
    db_user = db.query(User).filter(User.id == user_id).first()
    if db_user:
        db_user.is_active = True
        db.commit()
        db.refresh(db_user)
    return db_user
```

## 2. `async` / `await` とは何か

### 結論
「時間がかかる処理が終わるのを待ってから、次の行に進む」ための仕組み。

### なぜ必要か
サーバーとの通信には時間がかかる。何も工夫しないと、サーバーの返事を待たずに次の処理（画面の更新など）が先に進んでしまい、「サーバーは失敗したのに画面だけ更新された」というズレが起きる。

### 役割
| 部分 | 役割 |
|---|---|
| `async (id) => {...}` | 「この関数には待つ処理が含まれている」という宣言 |
| `await 何か` | 「ここで一旦停止して、結果が返るまで次の行に進まない」という指示 |

`await`は`async`が付いた関数の中でしか使えない。

### `await`を忘れるとどうなるか
サーバーの処理を待たずに次の行が実行されてしまう。見た目上は動いているように見えても、エラーハンドリング（`try/catch`）が効かなくなったり、画面とDBの状態がズレたりする。

## 3. `deactivateUser`関数の解説（`src/hooks/useUsers.ts`）

```ts
const deactivateUser = async (id: number) => {
  await api.patch<User>(`/users/${id}/deactivate`);
  setUsers((prev) => prev.filter((u) => u.id !== id));
};
```

| コード部分 | 説明 |
|---|---|
| `const deactivateUser = ` | `deactivateUser`という名前の箱を作り、関数を入れる。他のファイルから名前で呼び出せるようになる |
| `async (id: number) => {...}` | アロー関数。`id`は数値のみ受け取ると型で約束している（TypeScriptがミスを事前に教えてくれる） |
| `api.patch<User>(...)` | `api.ts`のPATCH用関数を呼ぶ。`<User>`は「結果はUser型で返る」という指定（ジェネリクス） |
| `` `/users/${id}/deactivate` `` | テンプレートリテラル。`${id}`部分に実際の値（例: 19）が差し込まれ、`/users/19/deactivate`という文字列になる |
| `await` | サーバーからの返事を待つ |
| `setUsers((prev) => prev.filter(...))` | Reactの状態更新関数。直前の状態(`prev`)を安全に参照しながら、無効化したユーザーだけを取り除いた新しい配列に置き換える |
| `prev.filter((u) => u.id !== id)` | JavaScript標準の`filter`。「条件に合うものだけ残して新しい配列を作る」機能。ここでは「無効化したidと一致しないユーザーだけ残す」 |

### 日本語訳
「`id`を受け取り、まずサーバーにPATCHリクエストを送って無効化してもらう。それが完了するのを待ってから、画面上の一覧からそのユーザーを取り除く。」

## 4. `api.patch`の解説（`src/lib/api.ts`）

```ts
patch: <T>(path: string, body?: unknown) => request<T>(path, { method: "PATCH", body }),
```

| コード部分 | 説明 |
|---|---|
| `patch: ...` | `api`というオブジェクトの中の1項目。`api.patch(...)`の形で呼び出せる |
| `<T>` | ジェネリクス。呼び出す側が「結果の型」を指定できる |
| `path: string` | 送り先URLの一部。文字列必須 |
| `body?: unknown` | 送るデータ。`?`が付いているので省略可能。PATCHは「更新するデータがない」場合もあるため |
| `request<T>(path, { method: "PATCH", body })` | 共通処理の`request`関数に、「PATCH方式で送ってね」という設定と一緒に丸投げする |

### なぜこんなに短いのか
実際の通信処理（トークンの付与、エラー処理など）は`request`関数に集約されている。`get`/`post`/`put`/`patch`/`delete`はすべて「メソッドの種類が違うだけ」の薄いラッパー（包み紙）になっている。

## 5. `request`関数の解説（`src/lib/api.ts`の本体）

```ts
async function request<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const { method = "GET", body } = options;
  const token = Cookies.get("access_token");

  const res = await fetch(`${BASE_URL}${path}`, {
    method,
    headers: {
      "Content-Type": "application/json",
      ...(token && { Authorization: `Bearer ${token}` }),
    },
    body: body ? JSON.stringify(body) : undefined,
  });

  if (!res.ok) {
    const error = await res.json().catch(() => ({}));
    throw new Error(error.detail || `HTTP error: ${res.status}`);
  }

  const text = await res.text();
  return text ? JSON.parse(text) : ({} as T);
}
```

| コード部分 | 説明 |
|---|---|
| `options: RequestOptions = {}` | 引数が渡されなければ空のオブジェクトを使う（デフォルト値） |
| `const { method = "GET", body } = options` | 分割代入。`options`から`method`・`body`を取り出す。`method`が指定されなければ`"GET"`を使う |
| `Cookies.get("access_token")` | ブラウザに保存されたログイン用トークンを取得 |
| `` fetch(`${BASE_URL}${path}`, ...) `` | JavaScript標準の通信関数。URLを組み立てて送信 |
| `...(token && { Authorization: ... })` | `token`がある時だけ`Authorization`ヘッダーを追加するテクニック（`&&`は左がfalseなら右を評価しない性質を利用） |
| `body: body ? JSON.stringify(body) : undefined` | 送るデータがあればJSON文字列に変換、なければ何も送らない |
| `if (!res.ok) { ... throw new Error(...) }` | サーバーが200番台以外（エラー）を返したら、エラーメッセージを作って例外を投げる |
| `res.text()` → `JSON.parse(text)` | 返事の中身を一度文字列として受け取り、空でなければJavaScriptのオブジェクトに変換する（削除・無効化のように返り値が空のAPIでもエラーにならないようにする安全策） |

### 全体の役割
「Cookieからログイン情報を取り出し、それを含めてサーバーに通信を送る。失敗したら分かりやすいエラーを投げ、成功したらデータを使える形にして返す」という**通信の面倒ごとを1箇所に集約**している。

## 3. ミドルウェアの認証ロジック修正

**該当ファイル**: `frontend/src/proxy.ts`

### 何が起きていたか（3段階で変化した）

**第1段階（最初の状態）**: 保護パスの指定漏れ
```typescript
const PROTECTED_PATHS = ["/profile", "/matching", "/chat"];

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const isProtected = PROTECTED_PATHS.some((path) =>
    request.nextUrl.pathname.startsWith(path)
  );

  if (isProtected && !token) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  return NextResponse.next();
}
```
`/`（トップページ）が`PROTECTED_PATHS`に含まれていないため、未ログインでもトップページに入れてしまっていた。

**第2段階（修正の途中でバグを埋め込んだ状態）**: 変数名だけ変えて中身を変え忘れた
```typescript
const PUBLIC_PATHS = ["/profile", "/matching", "/chat"];  // ← 名前だけ変えて中身はそのまま

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }
  return NextResponse.next();
}
```
`/login`自体が`PUBLIC_PATHS`（実質は保護パスの中身のまま）に含まれないため、`/login`にアクセス→保護パス扱い→`/login`にリダイレクト→また保護パス扱い…という**無限ループ**が発生した（`ERR_TOO_MANY_REDIRECTS`）。

**第3段階（最終的な正しい状態）**: 中身を実際の「公開パス」に修正
```typescript
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";

const PUBLIC_PATHS = ["/login", "/register"];  // ← 中身を実際に公開ページに

export default function proxy(request: NextRequest) {
  const token = request.cookies.get("access_token");
  const { pathname } = request.nextUrl;

  const isPublic = PUBLIC_PATHS.some((path) => pathname.startsWith(path));

  if (!token && !isPublic) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  if (token && isPublic) {
    return NextResponse.redirect(new URL("/", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"],
};
```

**学びポイント**: 変数名（`PUBLIC_PATHS`）と中身が矛盾していると、コードを読むだけでは気づきにくいバグになる。「公開パス方式」と「保護パス方式」のどちらで書くか、途中で混ぜないことが大事だった。

**補足**: `proxy.ts`というファイル名は、当初「Next.jsに認識されないので`middleware.ts`にリネームすべき」と誤って助言したが、Next.js 16では`middleware.ts`から`proxy.ts`への名称変更が公式に行われており、`proxy.ts`のままで正しいと後に訂正した。

## 4. ユーザー削除の500エラー → 論理削除方式への変更

### 何が起きていたか
削除ボタンを押すと`Failed to fetch`エラー。ブラウザのコンソールにはCORSエラーのように表示されるが、実体は**バックエンドの500エラー**だった。

原因は、削除対象のユーザーが`likes`（いいね）や`messages`（メッセージ）テーブルで他のユーザーと紐付いており、外部キー制約（`ON DELETE CASCADE`が未設定）に違反して`IntegrityError`が発生していたこと。FastAPI/Starletteは未処理の例外が起きるとCORSヘッダーを付与できず、ブラウザ側では「CORSブロック」に見えてしまう。

### 対応方針
物理削除（`DELETE`）をやめて、`is_active`フラグを`False`に切り替える**論理削除方式**に変更。

### `crud/user.py`

変更前: `is_active`の絞り込みなし

```typescript
  put: <T>(path: string, body: unknown) => request<T>(path, { method: "PUT", body }),
  delete: <T>(path: string) => request<T>(path, { method: "DELETE" }),
};

// 変更後
type RequestOptions = {
  method?: "GET" | "POST" | "PUT" | "PATCH" | "DELETE";  // ← PATCHを追加
  body?: unknown;
};
export const api = {
  get: <T>(path: string) => request<T>(path),
  post: <T>(path: string, body: unknown) => request<T>(path, { method: "POST", body }),
  put: <T>(path: string, body: unknown) => request<T>(path, { method: "PUT", body }),
  patch: <T>(path: string, body?: unknown) => request<T>(path, { method: "PATCH", body }),  // ← 追加
  delete: <T>(path: string) => request<T>(path, { method: "DELETE" }),
};
```
